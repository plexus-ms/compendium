A CI/CD system needs state (what exists), events (something changed), and procedures (make it so).
Plexus puts state in git, takes events from a forge someone else operates, and runs only stateless procedures.
This module is the pipeline that results: a reusable workflow in `plexus-ms/ci-cd` that knows verb names and never incantations, mounted on a tenant repo's push events by a generated workflow that carries only the tenant slug and a deploy host.


## § 1 The pipeline

> - A tenant MUST NOT operate its own CI control plane.
> - The forge SHOULD be GitHub; a tenant SHOULD NOT self-host a forge.
> - A tenant repo's CI MUST reach the repo only through its standard verbs ([§ 3 PLX-Repo](../contracts/repo.md)) and the image build of [§ 7 PLX-App](../contracts/app.md).

One reusable workflow runs check → test, then builds the image hermetically and pushes it, tagged with the git SHA.
Every stage that touches the app runs through its contract verbs; the image push is the workflow's own step.
There is no setup stage: verbs prepare what they need, so the check job is literally checkout → toolchain → verbs.
That indirection is what keeps one workflow tenant- and stack-neutral.
Path-scoping ([§ 2 PLX-Release](release.md)) is itself a mounted verb, not YAML logic: a `changed-apps` verb reads git and the workspace graph to print the apps whose sources changed (dependents included), a thin `changes` wrapper emits that set as a matrix, and a per-app `pipeline` wrapper (ci + deploy) fans out over it, so a docs-only push builds nothing and an unchanged app is neither rebuilt nor redeployed.
The tenant's own workflow is generated by the preset and shipped on the train, not hand-owned; it carries only the tenant slug and a `DEPLOY_HOST` variable.
Push to an environment branch composes the whole flow: `push → changes (verb) → per-app CI (verbs, image build) → deploy verb (pull, migrate, up, healthcheck, rollback-on-fail)`, continuous behaviour from a continuous event source, with nothing of the tenant's running continuously.

GitHub Actions *is* a control plane, but one someone else operates, with git as input; that is the allowed shape.
The forge is tier-0 for deploys either way: CI is the deploy trigger and GHCR holds the images, so a forge outage means no automated deploys.
What bounds the damage is the usual pair: running systems keep running and git is distributed, so an outage costs deploy availability, never data; and the verbs stay hand-runnable, so a forge-less deploy remains possible, just not convenient.
Not-self-hosting avoids *operating* tier-0, not *depending* on it; code and CI configs are not personal data, and a self-hosted forge would be a tier-0 dependency the tenant has to secure and back up before it protects anything.

Leaving GitHub means adjusting the mounts, never the logic: the workflow wrappers are dumb mounts over hand-runnable verbs, so a tenant on another forge rewrites a few YAML files and keeps every script.


## Maintaining

`plexus-ms/ci-cd` ships both halves and tags them together, so a wrapper always checks out its verb at the same tag.
The layering is load-bearing:

- **Verbs** are portable bash scripts in `scripts/` that contain *all* the logic and stay hand-runnable: `git clone && ./scripts/deploy.sh deploy@host tenant app image` works with no forge at all.
  This is what passes the degradation test.
  Change detection is a verb too: `./scripts/changed-apps.sh <from-sha> [<to-sha>]` prints the apps whose sources changed since a ref, dependents included, reading only git and the workspace graph.
  Bash's native failure modes (unset variables expanding to nothing, pipelines failing silently) are second-reader traps, so a safety baseline applies to every verb: strict mode (`set -euo pipefail` or equivalent) and shellcheck-clean, enforced mechanically at the repo boundary by `mise :check`, never the honor system.
  A verb's remote half is a quoted heredoc that ssh feeds to `bash`; `check` runs shellcheck over that too, and the heredoc can be extracted and run against a scratch directory with fake `docker` and `curl` scripts on `PATH` to exercise failure and rollback paths offline.
- **Workflow wrappers** are thin reusable GitHub workflows that merely mount a verb on the forge's events: checkout, secrets plumbing, one invocation.
  `changes.yml` mounts `changed-apps` and emits a matrix; `ci.yml` runs the verbs and builds the image; `deploy.yml` mounts the deploy verb; `pipeline.yml` composes `ci.yml` + `deploy.yml` for one app so the tenant can fan out per changed app.
  Logic never lives in the YAML.
  GitHub's workflow format is not an open standard, the runner is self-hostable but GitHub remains the scheduler, so the wrapper is forge-specific and disposable, while the verb is portable and permanent.

Tenant workflows reference the wrappers by the train tag, so the update bot ([PLX-Updates](updates.md)) carries each train to every tenant as a reviewed PR.
